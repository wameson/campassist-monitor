# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- **Spec:** `PLAN.md` in this repo is the **backend** design and phase plan (schema, migration + drift-guard rules, monitor workflow, poll/alert pipeline, provider seam, backend phases 1/7/8/12/13a and 13c's backend item). The **iOS/product** plan is `PLAN.md` in `~/workspace/firstmate/projects/camp-assist/` — read-only, lives outside this repo. The README summarizes the operator-facing parts.
- **Test:** `pytest` (config in `pytest.ini`; it puts the repo root, `scripts/`, and `tests/` on `sys.path` — modules import as `trigger_lambda`, `monitor`, `apns`, `db`, `common`, `providers.*`, fakes from `tests/helpers.py`). Python 3.12; install with `pip install -r requirements-dev.txt`. The suite must stay fully offline: no network, no real secrets.
- **Sharp edges:** runtime deps are deliberately capped at `httpx[http2]`, `PyJWT`, `cryptography`. A no-change monitor cycle has **two** budgets. Writes: ≤5 Supabase writes (`test_write_budget` enforces it) — don't add per-watch writes. Wall clock: Actions bills per job rounded up to the whole minute, so a no-change cycle must finish inside ~60 s or every run costs double; an unconditional `sleep` is the expensive thing, not a request. That is why `START_JITTER_MAX_SECONDS` is 20 s and not the 240 s it was until 2026-07-28, when a 226-run measurement found 92% of the billed minutes were `time.sleep()` (PLAN.md's minutes-budget table carries the arithmetic). The jitter is kept nonzero only because the trigger is planned to move to an exact-wall-clock external cron; per-request politeness is the separate `INTER_REQUEST_DELAY_RANGE`, which is not a cost lever and stays. `scripts/*` take injectable HTTP clients/clocks; keep new code testable the same way. Never poll recreation.gov in tests; use `tests/fixtures/`.
- **Provider seam:** `monitor.run` is provider-neutral. Everything site-specific — request host, parsing, normalization to the shared `{site_id: {"campsite_id","site","dates"}}` availability shape, booking URL — lives behind the `Provider` protocol (`scripts/providers/base.py`), one conformer per `watches.provider` value, registered in `scripts/providers/__init__.py` (README "Providers"). Watches route by their `provider` column; a provider this build does not register is skipped untouched, never errored. Keep new cycle code provider-agnostic, and keep `PollKey[0]` the watch's own `campground_id` — the 404-strike lifecycle and `campgrounds_polled` are campground-scoped. Poll dispatch is anchored to the provider, never to the client-writable `campground_id`: the cycle plans `monitor.PollUnit` pairs (provider name, `PollKey`) via `poll_dispatch`, and the 404-strike inputs (`not_found`, `polled_ok`) plus the `extract_relevant` slice each conformer sees are per-provider, so a `campground_id` two providers share can never cross between them. Primitives both layers need (`as_date`, `capped_line`, `MAX_ERROR_MESSAGE_CHARS`) live in `scripts/common.py` so a provider never imports `monitor` (which imports it). Two invariants any new conformer must respect: `watches.campground_id` must match `monitor.CAMPGROUND_ID_RE` (`[A-Za-z0-9_-]+`) whatever the site's own id scheme looks like — anything else is errored before it is ever polled, so a namespaced id needs `gtc_…`, not `gtc:…`; and `poll_plan` runs **outside** the cycle's per-watch containment (`poll_dispatch`), so it must never raise — a watch it cannot plan for (e.g. an unusable `provider_ref`) plans nothing, and `extract_relevant`, which does run inside containment, is where that failure is raised. A watch a conformer can *never* poll (client-written provider config it cannot read) must not fail every cycle forever while looking healthy to its user: the conformer says so through the optional `unpollable_reason(watch)` hook (`providers.unpollable_reason`, which defaults to pollable so a provider without client-written config need not implement it) and the cycle errors it once, like a malformed `campground_id` — unless the condition is pool-wide (it crosses `is_systemic` against the active pool), which is left `monitoring` and reported as a cycle failure instead, because broad breakage is the operator's to fix and nobody should have to recreate a watch over it. That hook also runs outside containment, so it must not raise, and its reason string reaches the operator channel — name the field, never the client's value. Symmetrically on the poll side: `poll` returning None means *transient* (keep the old hash, retry next cycle), so a per-unit fault no retry can clear — going_to_camp's `ParkTooLarge`, a park past the `MAX_CHILD_MAPS` safety cap — is **raised** instead, and the cycle's poll loop contains it as a cycle failure so the run goes red rather than leaving a park permanently unserved behind a green exit code.
- **Cycle resilience — containment & exit status:** per-watch work in `monitor.run` is contained — one watch's failure must never abort the cycle, and end-of-cycle bookkeeping (`run_summaries`, pruning) must always run. New watch writes go through `patch_watches` (batched, per-id fallback) and new failure paths through `record_failures`, so they count toward the systemic threshold that decides the run's exit status. A watch moves to `status='error'` **only** for a failure a write pinned to its own row (`PatchOutcome.isolated` / `isolated_failure`); table-scoped `sent_alerts`/APNs failures use `unattributed_failure` and must not error the watch. Keep loud failures loud: systemic breakage must still exit non-zero (README "Errors and run status").
- **`status='error'` is terminal, so it must stay visible and explain itself.** Nothing writes the status back to `monitoring`, and the cycle's only `watches` read filters `eq.monitoring` — an errored watch is *absent*, which once left 3 of 5 watches dead for two days behind green runs with `errors: null`. Two rules keep that from recurring, both provider-neutral and both in `monitor.run`: every cycle counts the `status=eq.error` population still worth acting on (`end_date=gte.<today>`, so a warning cannot fire forever; one extra select, **no per-watch writes** — the ≤5 budget covers it) and puts the count on the world-readable row with the per-reason breakdown operator-only; and **every** `status='error'` write goes through `write_errored`, never a bare `write_watches`, so it carries a value from the fixed `ERROR_REASONS` vocabulary (README "Watch lifecycle"). A new error site therefore needs a reason, not a new string — the values are what a future retry policy classifies on. `watches.error_reason` is the one WARN column the monitor *writes*: the classification is earned by `write_errored` retrying once without the column when `rejects_missing_column` recognizes a missing-column rejection naming it (`42703` or PostgREST's write-body `PGRST204`, matched on `message` alone — `details`/`hint` echo row values), then dropping it for the rest of the cycle. That reason-carrying attempt also vetoes the per-id fan-out for exactly that signature (`patch_watches(fanout=…)`), so an unapplied 0004 literally costs one extra write and charges the `FanoutBudget` nothing; every other rejection still fans out, because the 404 site needs isolation to error a genuinely bad row. Both the census and the breakdown are bucketed, never echoed — `error_reason` and `campground_id` are client-writable. Automatic re-arming of errored watches is deliberately out of scope (captain, 2026-07-27): reason data first.
- **APNs rating:** pass `rated=False` only for a per-device rejection (a dead device token / unbuildable push URL — `apns` `PERMANENT_FAILURE`): reported to both audiences but kept out of the exit-status rate. A pool-wide provider/config fault (`CONFIG_FAILURE` — expired/invalid/missing provider token, bad/disallowed topic) and every `RETRYABLE_FAILURE` (429/5xx/transport) stay rated, so a signing-key or bundle-id outage exits non-zero. A distinct backstop (`APNS_WIPEOUT_RATE`/`_FLOOR`) additionally turns the run systemic when outright rejections wipe out nearly every served push, catching reason codes `send_alert` does not enumerate.
- **Two rendering channels:** `run_summaries.errors` is **world-readable**, so it gets the `safe=True` rendering of `summarize_exception` (no watch UUIDs → per-run ordinals, no PostgREST `details`/`hint`, and for an exception with no response only its type name); the operator-only Action annotation gets the full rendering via `errors_detail`. Rules that keep this true as code is added: a failure reaches the row only through a rendering path (`watch_failures` per-watch, `record_cycle_failure` for the rest) — never by appending a pre-formatted message to the shared `errors` list, which is copied into the row verbatim, so anything that knows a watch id (e.g. `apns.send_alert`) hands back the *exception* and lets `run` attribute and render it; a user-supplied value (a rejected `campground_id`) reaches `errors` only as an aggregate count, with the value going to `detail_only`; everything on the shared channel goes through `capped_line` (which bounds the whole composed line, prefix included); and each cycle failure travels one channel per audience (`public_cycle_failures` → the row, `cycle_failures` → `cycle_errors`), because `failure_annotation` joins `errors_detail` and `cycle_errors` and a copy in both prints twice.
- **Schema changes:** editing `supabase/schema.sql` only affects fresh installs. Existing live DBs drift unless you also add an idempotent `supabase/migrations/NNNN_<desc>.sql` (see README "Database migrations") **and** the column's entry in `preflight.REQUIRED` (`scripts/preflight.py`), classified `WARN` only with a cited fallback proving the monitor tolerates its absence — otherwise `HALT` (the conservative default is a gate, not advice; a test holds the manifest to `schema.sql` in both directions). **Ordering:** apply the migration by hand in the Supabase SQL editor **first**, then merge the manifest entry — a `HALT` entry merged ahead of the apply halts every cycle until an operator reaches the SQL editor, which is the zero-monitoring window the guard exists to avoid. Migrations are applied **manually** in the Supabase SQL editor by design — CI does not run them, and the preflight only detects (never applies) drift. `watches.provider_ref` is client-writable and carries identifiers only (`resource_location_id`, `map_id`); a provider's request host/URL is hardcoded/allowlisted in code and must **never** be derived from `provider_ref` (SSRF).
- **GoingToCamp request posture:** keyless GET, plus **one read-only pricing POST** (`/api/resource/feeDetails`, which answers `405` to a GET — captain-approved, empty body, no cart/cookie/token, not in the polling loop); still **never drive a browser** at this host, whose SPA is Azure-WAF captcha-gated while `/api/*` is not. Every URL is a constant in `going_to_camp.py`. Beyond availability, a poll reads the park's resource catalog (`/api/resourcelocation/resources`) for the real site labels plus the ADA-Only / capacity / equipment / hookup detail, decoded through `/api/attribute/filterable` and `/api/equipment`; all three are cached for the life of the process (one process = one cycle; `clear_metadata_cache()` and `tests/conftest.py` keep that from leaking between tests). Two rules that layer on the availability parse's "unknown means taken": the catalog is **cosmetic** — a park whose catalog a cycle cannot read still polls, hashes and alerts with the `resourceId` fallback, never a failed unit — and every metadata field is **unknown, never no** when the platform did not publish it, because a filter built on one must fail open (a suppressed opening is invisible to the user). Enum indices mean nothing on their own (`0` is "Yes" on ADA Only and "Not Available" on Pad Location), so a Yes/No attribute is resolved through the vocabulary, never cast; the pinned definition ids and the electric`{5,6,7}`≠water`{6,7}` sets are held to the captured vocabulary by a test so a renumbering upstream goes red instead of silently decoding nothing.
- **The ADA-Only exclusion** is the one place a metadata field changes what the cycle alerts on, and it is `going_to_camp`'s `extract_relevant` alone — recreation.gov never filters and never reads the column, by captain decision (its `is_accessible` means the site *has* accessibility features, not that it is reserved; README "Providers"). Three placement rules hold it together, each with a test: it runs **after** the `site_ids` match and only for an undirected watch (a user who named the site outranks the filter), **before** the caller hashes the shape (so an ADA-only site opening and closing is not a delta and costs no write), and it drops only a site the catalog **positively** marked, so any unreadable catalog/vocabulary suppresses nothing. The per-watch opt-in is read `bool(watch.get("include_ada_only"))` — `.get` with a default is exactly what keeps that column `WARN` in `preflight.REQUIRED`, so a read that ever subscripts it has to be reclassified `HALT`. `use_direct` follows recreation.gov here, not going_to_camp: its grid carries an `IsAda` flag but the conformer reads neither it nor `include_ada_only`, because `IsAda` is not established to mean *reserved* and suppressing on an unproven designation is the exact "hide bookable sites" harm the exclusion guards against.

- **UseDirect (`use_direct`, `going_to_camp`'s multi-tenant sibling).** The Tyler platform behind ReserveCalifornia. **Shared wire contract this conformer owns** (the iOS app builds to it): `watches.provider = 'use_direct'`, and `watches.campground_id = '<tenant>_<facilityId>'` (a registered tenant key + `_` + the UseDirect FacilityId, e.g. `ca_377` — underscore, never colon, and the id carries the whole identity so `provider_ref` is unused). One read-only POST per (facility, stay) to `Tenant.grid_url`; no recursion and **no second catalog request** (the grid body already carries `UnitId`, `Name` and per-night `IsFree`). It is multi-tenant because UseDirect runs one host per state: the `use_direct.TENANTS` allowlist pins each tenant's host/path/booking-URL as vetted constants and the campground_id's tenant key only *selects* a row — never builds a host, so the SSRF invariant holds even though the id is client-written (**do not** infer a host from a pattern: California has left `*.usedirect.com` for a Tyler cloud host, so each state is pinned individually; NV/AZ/WY are not wired). Posture is captain-ruled: **one fixed honest UA, never per-request rotation** — the module uses the cycle's session UA verbatim and imports no UA generator (camply rotates a random Chrome UA on this exact POST as fingerprint evasion; a test asserts we do not). `poll` raises `FacilityTooLarge` past `MAX_UNITS_PER_FACILITY` — the single-POST analogue of `ParkTooLarge`. Enabling it took **only a CHECK-widening migration** (`0007`, hand-applied by the captain before the app ships UseDirect watch creation) — not a new column, so `preflight.REQUIRED` is unchanged and the `provider` column was already in the manifest.

- **One live entrypoint; a separate trigger that never polls.** The poll runs `python scripts/monitor.py` on GitHub Actions, unchanged, and **stays there** — PLAN.md Phase 17 is "AWS-triggered GitHub Actions": an AWS EventBridge Scheduler fires `monitor.yml`'s `workflow_dispatch` on the exact wall clock (fixing GitHub's 1–3 h `schedule` drift) while the poll itself never leaves Actions, the only egress GoingToCamp's Azure Front Door WAF accepts. **Why the split is surprising but deliberate:** two earlier plans tried to move the *poll itself* into a cloud and both were refused by the WAF — AWS Lambda (8×403) and the successor Azure Container Apps Jobs (probe 403) — so only the *trigger* moved. The dead AWS-poll artifacts (`lambda_function.py`, `tests/test_lambda_function.py`, the `make lambda-zip` `Makefile`, and `deploy.yml`) have been **removed** (the follow-up cleanup PLAN.md anticipated). One thing they motivated survives on purpose: `monitor.main(process_started=…)` is harmless plumbing that stays (the CLI path uses its import-time default). The Phase 17 trigger Lambda lives at **`trigger_lambda.py`** (repo root; handler `trigger_lambda.handler`; tests `tests/test_trigger_lambda.py`) — a function that reads a fine-grained PAT from SSM, POSTs `monitor.yml`'s `workflow_dispatch`, logs the HTTP status, and treats 204 as success and anything else as a raise (so a silent-miss trigger failure surfaces as a Lambda invocation error). It is **stdlib-only** (`urllib` + runtime `boto3`, injected for offline tests) so it deploys as a single file with no bundled dependency — do **not** give it `httpx` or a packaging build, and do **not** let it import `monitor`/`scripts.*`; it is deliberately separate from the poll pipeline. A late Phase 17 step flipped the repo public (Phase D, 2026-08-01), taking Actions minutes to $0.

- **Secret scanning (gated the Phase 17 public flip, now guards every PR since the history is permanently public).** `.github/workflows/secret-scan.yml` runs gitleaks (pinned, checksum-verified) on **every PR** and **fails** the check on any finding — it scans the PR's `base..head` commits with the full default ruleset and composes with the no-mistakes gate (README "Secret scanning"). Exemptions live in `.gitleaks.toml` as a **narrow allowlist** (one exact fake-token string from `tests/test_trigger_lambda.py`, not a disabled rule or an exempted file) — never widen it to a whole file or a disabled rule. The one-time pre-public **full-history** gate is `gitleaks git --log-opts=--all`; it came back clean at 108 commits (the AWS **account ID** in `6090b18b`/`970ceee6` is captain-accepted, is not a credential, and gitleaks does not flag it — do not rewrite history for it). GitHub's own free push protection is a Phase D **repo setting** (operator's to enable), documented but deliberately not implemented here.
